# Day 15: Virtual Environments & pip — Notes

## 1. Revision Notes

**The problem:** every package used across this bootcamp so far had been installed globally, shared across every Python project on the machine. That's fine until two projects need different, incompatible versions of the same package — then something has to break.

**The fix:** a virtual environment (`venv`) is an isolated copy of Python + pip, scoped to one project folder. Packages installed inside it exist only there.

**Discovery today:** despite the original project setup (Day 1) assuming a venv from the start, Days 1–14 actually ran against the global Python install the entire time — no `(venv)` prefix ever appeared in any terminal output before today.

**The core commands:**
```bash
python -m venv venv          # create it
venv\Scripts\activate         # activate it — (venv) prefix confirms success
pip install -r requirements.txt
deactivate                    # leave it
```

**Proof of isolation, in practice:** `pip list` right after activating a fresh venv shows almost nothing (`pip` only) — everything global was left behind. Later, `pytest -v`'s own header line shows exactly which `python.exe` it's running against — a direct way to confirm code is executing inside the venv, not the global install.

**Activation is per-terminal, not global.** Every new terminal session needs `venv\Scripts\activate` run again, unless VS Code's "Activate Environment On Terminal Creation" setting is enabled *and* the correct interpreter is selected — in which case it happens automatically.

**Real gotcha hit conceptually today (not literally, but worth remembering):** `requirements.txt` using `>=` minimums (`pandas>=2.0.0`) can silently pull in a much newer major version (`pandas 3.0.5` installed instead of anything close to `2.0.0`). `pip freeze > requirements.txt` avoids this by pinning exact versions — a tradeoff between "always get the latest" and "always get exactly what was tested."

**`venv/` should never be committed to Git** — it's large, machine-specific, and regeneratable from `requirements.txt` alone. Already excluded via `.gitignore` from Day 1.

## 2. Cheat Sheet

```bash
# One-time setup
cd path\to\project
python -m venv venv

# Every work session
venv\Scripts\activate          # (venv) prefix = active
pip install -r requirements.txt   # only needed after requirements.txt changes
# ... do work ...
deactivate                     # when done

# Verify isolation
pip list                       # should show only what THIS project installed

# Verify which Python is actually running
pytest -v                      # header line shows the exact python.exe path used

# Capture exact installed versions (alternative to hand-written >= minimums)
pip freeze > requirements.txt
```

**PowerShell execution-policy fix, if activation is blocked:**
```bash
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

**VS Code:** `Ctrl+Shift+P` → "Python: Select Interpreter" → `.\venv\Scripts\python.exe`
